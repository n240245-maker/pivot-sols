## Backend and database — Railway manual alternative

Use only if the owner elects to create a new Railway project. [Railway PostgreSQL](https://docs.railway.com/databases/postgresql) exposes a private `DATABASE_URL` for services in the project. Add PostgreSQL first, then a backend service from the repository with **root directory `backend`**. Use `backend/Dockerfile` or Railway's Python builder; do not mix two conflicting start commands. With the Dockerfile, the entry point is `uvicorn main:app --host 0.0.0.0 --port ${PORT:-8000} --workers 1`. **Run migrations before opening traffic**: either set the Railway start command to `alembic upgrade head && uvicorn main:app --host 0.0.0.0 --port $PORT --workers 1` when using a Python builder, or run `python -m alembic upgrade head` through [Railway SSH](https://docs.railway.com/cli/ssh) before the Docker service serves CMS traffic. Do not assume the Dockerfile currently auto-migrates.

On the backend service set `DATABASE_URL` as a reference to the Railway PostgreSQL connection, plus `FRONTEND_URL`, `OTP_SECRET`, `CONTACT_TO_EMAIL`, and email settings. For a no-paid deployment choose `EMAIL_PROVIDER=brevo`, `BREVO_API_KEY`, `SMTP_FROM_EMAIL`, `SMTP_FROM_NAME`; Railway Free/Hobby SMTP is unavailable. If the account later has Pro and SMTP is desired, set `EMAIL_PROVIDER=smtp`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, sender fields. The database factory accepts Railway's PostgreSQL URL and selects `psycopg`; keep the URL private. Generate a public HTTPS backend domain, check `/api/health`, and save the exact origin for Vercel.

To import the private snapshot into Railway PostgreSQL, run the import from a process that can reach the DB and has the snapshot file. One option is a short-lived secure task/SSH session with the file available to that session. Another is Railway's [TCP proxy/public database URL](https://docs.railway.com/databases/postgresql) for a local import; this may incur egress usage, so enable it only during import, never publish the URL, and disable it afterward. In an interactive terminal, point a **temporary** `DATABASE_URL` at that public URL, run `python -m alembic current` then `python scripts/transfer_content.py import C:\SECURE\content-export.json`, and clear it. `python scripts/create_admin.py` needs an interactive TTY; run it locally against that temporarily reachable production DB or through Railway SSH. Do not copy local admin password hashes or sessions. Verify admin exists by logging in, not by printing the password hash.

A full `pg_dump`/`pg_restore` would move auth tables, expired sessions and QA rows; it is **not recommended** for this project's first deployment. If needed for a later full-database move, use PostgreSQL client tools with a private [PostgreSQL password file](https://www.postgresql.org/docs/current/libpq-pgpass.html), never a password literal on the command line. On a **new, empty, unmigrated** destination only, the conceptual commands are:

```powershell
pg_dump --format=custom --no-owner --no-acl --host LOCAL_DB_HOST --username pivot_admin --dbname pivot_sols --file C:\SECURE\pivot-full.backup
pg_restore --no-owner --no-acl --single-transaction --host PROD_DB_HOST --username PROD_DB_USER --dbname PROD_DB_NAME C:\SECURE\pivot-full.backup
```

Replace all uppercase placeholders locally. A full restore also copies the `alembic_version` row and admin state; do not run `alembic upgrade head` before restoring that full dump. Inspect the destination and backup before any restore. Never use `--clean`, `DROP DATABASE`, `TRUNCATE`, or `pg_restore --clean` against valued data without specific authorization. The content-only import above is safer for this project.

Note the **actual** frontend URL and set backend `FRONTEND_URL` to that exact origin. Redeploy/restart the backend after changing its environment. Test direct refreshes of `/login`, `/dashboard`, `/admin/login` and a deep resources path. [Vercel documents external rewrites](https://vercel.com/docs/routing/rewrites).

## Security and acceptance

Vercel gets no database, SMTP, Brevo or OTP secret. Admin authentication is server-backed: Argon2id password, emailed challenge, PostgreSQL session, revocation, exact Origin and CSRF checks. Frontend admin fetch uses credentials. Student OTP verification now creates a PostgreSQL-backed, revocable, absolute 30-day session; the browser stores only an opaque HttpOnly cookie. The production `/api` proxy keeps the cookie on the frontend site. Student profile data entered at login is not independently verified against a campus registry. Student route access never grants admin API access.

The student OTP store and contact throttles are in one backend process. Keep one worker/instance; restarts invalidate pending student codes. Public CMS APIs show only published rows with published ancestors. CMS updates live in PostgreSQL and appear on student refresh/navigation without a code redeploy.
